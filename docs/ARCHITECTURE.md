## Database — Postgres (via Neon)

### Context

The natural data model for a Kanban board is relational: boards contain columns, columns contain cards. The hard engineering problems — ordered card lists under concurrent moves — map cleanly onto SQL primitives.

### Decision

Use Postgres (hosted on Neon), accessed via Prisma.

### Why

- **Transactions.** Moving a card is multi-row: update the card, possibly reorder siblings, emit a change notification. First-class SQL transactions make this atomic without external coordination.
- **Relational structure.** Cascading deletes, foreign keys, and uniqueness constraints live in the schema — not scattered through application code.
- **Row-level locking.** `UPDATE ... WHERE version = ?` is the complete conflict-resolution story. No external lock service needed.
- **Dual role.** Postgres `LISTEN/NOTIFY` doubles as the pub/sub bus (see below), removing Redis as a v1 dependency.
- **Analytics stay simple.** Cycle time, lead time, WIP per column are one SQL query each.

### Trade-offs

- Real migrations (Prisma Migrate) are required. Slightly higher ceremony than schemaless alternatives.
- `LISTEN/NOTIFY` scales to roughly thousands of events per second per connection — fine for v1; see the fan-out section for upgrade triggers.

### Alternatives considered

- **MongoDB.** Familiar but wastes the relational structure; multi-document transactions are slower in practice.
- **SQLite.** Zero-ops but no realtime fan-out story; concurrent writes serialize.
- **PlanetScale.** No foreign keys, no `LISTEN/NOTIFY` — the same drawbacks as Mongo for this shape.

## Card position — Fractional indexing

### Context

Cards within a column have an order. The naive approach — an integer `position` column renumbered on every move — is `O(n)` writes per move and causes lock contention under concurrent users.

### Decision

Store `position` as a **lexicographically sortable string** generated by the [`fractional-indexing`](https://www.npmjs.com/package/fractional-indexing) npm package (the algorithm behind Figma and Jira's Lexorank).

### How it works

- Keys are strings like `"a0"`, `"a1"`, `"a2"`.
- Inserting between `"a1"` and `"a2"` generates `"a1V"` — still sorts correctly.
- `generateKeyBetween(prev, next)` produces a key that is strictly between the two inputs.
- A card move is one `UPDATE`. No sibling renumbering, ever.

### Trade-offs

- Keys get longer under many consecutive inserts between the same pair. Not an issue at Kanban scale.
- Occasional rebalancing may be needed in pathological cases — out of scope for v1.
- Database schema: `position TEXT NOT NULL`, with `UNIQUE (column_id, position)` and an index on `(column_id, position)` to serve ordered reads.

### Concurrency note

`generateKeyBetween` is deterministic — concurrent moves into the same gap produce identical keys. The move handler catches `P2002` unique-constraint collisions and retries with the upper bound tightened to the colliding key. Re-running the same generation with the same inputs would produce the same colliding key, so progress is guaranteed only by narrowing the range on each attempt.

### Alternatives considered

- **Integer `position` with renumber.** `O(n)` writes per move; lock contention under concurrency.
- **Float `position`.** Precision degrades after ~50 inserts between two cards.
- **Linked list (`prev_id` / `next_id`).** Complex updates, hard to query ordered.

## Fan-out — Postgres `LISTEN/NOTIFY` (not Redis)

### Context

Socket.io instances running on multiple nodes must share state so a message sent to one node reaches clients connected to another. The default pattern is Redis pub/sub via `@socket.io/redis-adapter`. That adds an additional managed service to run and pay for.

### Decision

Use **Postgres `LISTEN/NOTIFY`** as the fan-out bus in v1.

### How it works

- Each API node runs `LISTEN card_events` on a dedicated pg connection at startup (a pooled connection cannot hold a session-scoped subscription).
- Any state change calls `pg_notify('card_events', payload::text)` inside the same transaction as the write — delivery to listeners is contingent on commit.
- Each API node that receives the notification validates the payload against a Zod schema, then emits on the matching Socket.io room (`board:${boardId}`).

### Trade-offs

- `pg_notify` payloads are capped at 8 KB. Current payloads carry `{ type, boardId, data }` with only the changed fields and stay well under this.
- One Postgres connection per API instance is pinned for `LISTEN`. Fine at single-digit instance counts.
- `NOTIFY` is best-effort within a transaction block; the implementation emits as the last statement in the write transaction to make delivery contingent on commit.

### Upgrade triggers

Switch to Redis pub/sub (via `@socket.io/redis-adapter`) when any of these become true:

- More than roughly five API instances running concurrently.
- Notify payloads need to exceed 8 KB.
- Measured notify throughput approaches ~1000 per second sustained.

### Alternatives considered

- **Redis pub/sub.** Standard, scales further, requires one more managed service.
- **NATS.** Overkill for v1.
- **No fan-out, sticky sessions only.** Fails as soon as the API runs on more than one node.
